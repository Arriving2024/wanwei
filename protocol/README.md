# 万维计划：P0 最小互通契约

版本：`wanwei-p0/0.1`。更新：2026-10-15。Windows / Android 0.3.1 已在一组物理设备上完成双向固定 1 MiB 文件、保存及独立哈希验收，使用 USB 辅助控制；详细边界见[实测记录](../docs/p0-file-transfer.md)。0.3.2 开发中的[自动端口提示](rendezvous.md)独立于本文件协议，仍需普通流程真机验收。JSON 向量仍是输入与预期结果，不能将向量文件本身当作执行记录。

## 1. 本轮范围

一次经认证的 TCP/TLS 连接，只发送一个 1 MiB（1,048,576 字节）合成测试文件。反向测试建立新连接并交换发送、接收角色。P0 不提供用户文件选择、远程路径、目录、多文件、并发任务、续传、默认自动接收、网络远程命令或媒体传输。第 8 节的 USB 辅助入口仅供显式授权的调试实验，不改变网络协议或固定文件范围。

该字节流协议不建立无线链路。原生连接适配器必须先完成发现、系统配对、P2P 建链，提供实际本地/远端地址和端口、接口标识及证据编号；支持 IPv6 时保留作用域信息。文件发送方为 TCP 客户端，接收方为 TCP 服务端；二者不必对应 Wi-Fi Direct 的客户端/组主角色。

监听端仅绑定原生适配器提供的直连接口地址，发起端将 socket 绑定该直连接口/地址；不使用 `0.0.0.0`、`::` 或默认路由猜测直连路径。监听端口由系统分配，具体地址/端口由平台适配器交换，P0 不假定固定 IP 或端口。发现数据只用作连接线索，不是可信身份。无法选定及观测真实 P2P 路径时报告 `DIRECT_PATH_UNVERIFIED`，不静默改走普通局域网。

## 2. 认证与用户确认前置

- 使用平台维护的 TLS 1.3 实现；双方提供应用证书并验证握手中的持钥证明。禁用 0-RTT，P0 禁用会话恢复。不得自行实现密码算法，不允许明文或“信任所有证书”绕过。
- 每个应用安装生成自己的设备密钥，由平台保护存储保管。身份 `identity` 是证书公钥的 DER SubjectPublicKeyInfo 的 SHA-256，编码为 64 位小写十六进制。它不来自设备名、MAC 地址、发现广播或对端自行填入的 JSON。
- 首次信任前，双方用户通过当面扫描对方设备上显示的完整公钥指纹，或人工比对完整指纹，明确确认并保存该公钥绑定。二维码仅表达身份；不得借此导入任意路径或执行命令。此 P0 的人工步骤是实验配对入口，未来简化需另行设计和审阅。不能从未认证的网络消息中自动建立信任。
- 仅接受事先经用户确认的对端公钥；TLS 使用该公钥绑定的验证策略，验证证书适用性、有效期和握手证明。自签证书也不能通过通用的“忽略错误”回调放行。证书轮换且公钥变化需要重新确认。单纯系统 Wi-Fi 配对不能替代应用身份验证。
- TLS 完成后，`HELLO.identity` 必须等于当前 TLS 对端证书的上述指纹。认证失败在 TLS/连接层中止，不发送文件或应用成功消息。
- 已配对不表示允许收文件。普通模式每个有效 `OFFER` 仍由接收端用户明确接受，才可发送 `ACCEPT`。第 8 节允许操作者对指定公钥、固定 1 MiB 测试任务显式预授权，报告必须与人工点击接收区分。没有安全实现和确认入口时只能运行能力探测，不能开放真实文件接收端口。

TLS 的握手与加密交给标准库实现，参见 [IETF TLS 1.3 规范页面](https://www.rfc-editor.org/info/rfc9846/)。以上公钥确认、单文件限制及禁用恢复是本项目 P0 的应用策略。

## 3. 字节帧

TLS 解密后的连续字节流中，每帧为 `kind[1] || length[4] || payload[length]`。`length` 是无符号 32 位大端整数，只计 payload，不计 5 字节头。读写必须处理部分读写以及合并到来的多帧，不能把一次 socket 读取当作一帧。

| kind | payload | 长度限制 |
| --- | --- | --- |
| `0x01` | 一个 UTF-8 JSON 控制对象 | 1–4,096 字节 |
| `0x02` | 原始文件字节，不经过 JSON 或 Base64 | 1–65,536 字节，且不得超过剩余文件长度 |

其他 kind、长度为零、超上限、帧截断立即失败。先检查长度再分配缓冲区，不能按对端声明分配 4 GiB。所有实现累计字节计数至少使用无符号 64 位整数或可证明不溢出的等价类型；先比较 `length <= expectedSize - receivedBytes` 再累加。单次有效数据最多 1 MiB。

控制对象遵循 [JSON 标准](https://www.rfc-editor.org/info/rfc8259/)，本协议额外要求：无 BOM、严格 UTF-8、根节点为对象；字段恰好为下表列出的字段，拒绝重复键、未知键、缺字段、错误类型及非有限值。字符串枚举区分大小写；不允许通过隐式转换把字符串当数值。所有整数数字 token 仅允许 `0` 或 `[1-9][0-9]*`，拒绝负数、小数、指数、`-0`，并检查 `0..4294967295`，然后检查字段专用限制。数字字段不得解析后有损取整。字段顺序与无意义空白不影响合法性。

## 4. 控制消息

共同字段 `type` 是下表的大写类型。`transferId` 是发送端为每次新任务生成的 16 字节密码学随机数，编码为 32 位小写十六进制。一个连接只有一个任务；收到消息的任务 ID 必须与本连接 `OFFER` 完全一致，不可凭此 ID 跨连接恢复或覆盖文件。

| type | 所有其他必需字段 | 规则 |
| --- | --- | --- |
| `HELLO` | `version`, `role`, `service`, `identity` | `version` 固定字符串 `0.1`；`role` 为 `sender` 或 `receiver`；`service` 固定 `file.p0`；`identity` 为已认证 TLS 公钥指纹 |
| `OFFER` | `transferId`, `fixture`, `sizeBytes`, `sha256` | `fixture` 固定 `ramp256-1mib-v1`；`sizeBytes` 固定整数 `1048576`；`sha256` 固定为下节合成文件哈希 |
| `ACCEPT` | `transferId` | 仅接收端发出；用户确认且本地创建安全临时文件成功后发送 |
| `REJECT` | `transferId`, `reason` | 仅接收端发出；`reason` 为 `USER_DECLINED`、`NO_SPACE`、`BUSY` 或 `POLICY`，随后结束连接 |
| `COMPLETE` | `transferId`, `sizeBytes`, `sha256` | 仅接收端发出；字节数与实际内容校验正确、保存提交完成后发送；值与 `OFFER` 相同 |
| `ERROR` | `transferId`, `code` | 无有效 `OFFER` 时 `transferId` 为 JSON `null`，否则必须匹配任务 ID；`code` 见下表；任一方发出后结束连接 |

`service` 将来可以通过新版本增加媒体种类，本版本收到 `media.*` 必须返回 `UNSUPPORTED_SERVICE`，不得宣称已支持投屏。文件协议不会把媒体帧混入当前文件字节流。

| ERROR code | 含义 |
| --- | --- |
| `UNSUPPORTED_VERSION` | HELLO 版本不支持 |
| `UNSUPPORTED_SERVICE` | HELLO 服务不支持 |
| `INVALID_MESSAGE` | JSON/字段/数字/枚举/固定测试文件参数不合法 |
| `INVALID_FRAME` | kind 或帧长度不合法 |
| `UNEXPECTED_MESSAGE` | 状态、方向、角色或重复消息不合法 |
| `IDENTITY_MISMATCH` | HELLO 声称身份与已认证 TLS 公钥不一致 |
| `SIZE_MISMATCH` | 数据会超过协商大小，或 COMPLETE 字节数错误 |
| `HASH_MISMATCH` | 文件内容哈希或 COMPLETE 哈希不一致 |
| `STORAGE_FAILED` | 创建之后的写入、同步、提交失败 |
| `CANCELLED` | 任一用户取消尚未完成的任务 |
| `TIMEOUT` | 协议阶段超过规定等待时间 |
| `DIRECT_PATH_UNVERIFIED` | 运行中失去已验证的直连路径 |

错误回复仅在已认证且连接仍可用时尽力发送一次，不包含本地路径、系统异常或密钥。格式损坏、TLS 失败、对端关闭等情形可以直接关闭并在本地记录原因；不为回复 ERROR 无限等待。收到 ERROR 不再回复 ERROR。

## 5. 状态和完成语义

1. 双方原生适配器建立直连并绑定 socket；双方已确认的应用身份通过 TLS 双向认证。
2. 发送端发 `HELLO(role=sender)`。接收端验证后回 `HELLO(role=receiver)`；发送端验证其身份、版本和服务，然后发送 `OFFER`。
3. 接收端验证固定测试参数，提示用户允许接收 1 MiB 测试数据；拒绝则发 `REJECT` 并关闭。接受且临时文件创建成功则发 `ACCEPT`。
4. 发送端收到 `ACCEPT` 后发送 kind `0x02` 数据帧，直到合计恰好 `1048576` 字节。发送端继续读取可能提前到来的 ERROR，控制读不能等待所有写入结束。可采用 16 个 65,536 字节帧；也允许更小的合法分片。
5. 接收端顺序写入并计算 SHA-256。达到预期长度后停止接受更多 DATA，执行文件同步及本地保存提交，成功后才发 `COMPLETE`。没有额外的 DATA_END 帧、校验协议、分块序号或恢复请求。
6. 发送端验证 `COMPLETE` 的任务 ID、字节数和哈希后，才标记“对方已保存”；接收端在本地提交后可标记“本机已保存”。双方正常关闭 TLS 及连接适配器的本次会话资源。发送端未收到 COMPLETE 时只能记“未确认”，不能声称接收端没保存，更不能声称成功。

任何阶段不得出现第二个 OFFER；收到 ACCEPT 前不得传 DATA；接收端不得发送 DATA。拒绝、出错、取消、超时、截断是本连接终态。完成后收到新应用帧须拒绝，不能作为下一任务处理。TLS/连接中断不续传；重新发送使用新连接、新任务 ID，仍需用户接受。

P0 超时从相应阶段开始使用单调时钟计算：TCP/TLS 建立 30 秒，HELLO 交换 10 秒，等待用户接受 120 秒，开始传输后 30 秒无有效数据进展，最后一个数据帧发完后等待 COMPLETE 30 秒。每个头和控制 payload 读取自首字节起最多 10 秒，每个 DATA payload 自头读完起最多 30 秒。单次协议会话从 TLS 完成起绝对上限 180 秒。按先达到的限制中止，不能靠逐字节滴送无限延长。测试记录 timeout 原因，不能将超时归咎于系统兼容性而无证据。

## 6. 固定文件与安全保存

发送端本地生成 `bytes[i] = i % 256`，`0 <= i < 1048576`。预期 SHA-256：

```text
fbbab289f7f94b25736c58be46a994c441fd02552cc6022352e3d86d2fab7c83
```

不从网络接收文件名或路径。接收端在应用自己拥有的 P0 测试目录内独占创建本地随机名称 `.partial` 文件；最终文件名也由本地生成。禁止覆盖已有文件、跟随符号链接/重解析点或在应用目录之外写入。以平台适用的原子“不覆盖”提交或等价安全操作完成保存，提交前确保文件内容同步成功；若平台提供目录同步，提交后同步目录。P0 的保存确认表示操作系统持久化调用成功，不承诺电源故障时存储硬件的绝对持久性。

失败或取消清理本次未提交的临时文件，不清理其他任务或已有文件。空间不足在 ACCEPT 前可 REJECT，接受后则 STORAGE_FAILED。网络日志不输出私钥、证书秘密材料或用户文件路径。

Android 0.3.1 的提交实现不依赖硬链接：在应用拥有的 `0700` 测试目录内，以 `O_EXCL` 和 `O_NOFOLLOW` 独占创建本任务的随机临时文件与空的最终占位文件，保留对应文件描述符，核对目录与文件的设备/inode、所有者、类型和链接数后，原子 rename 仅替换本任务刚创建的占位文件。碰撞或任务开始前已存在的名称不能成为占位文件。该等价安全操作依赖应用私有目录与单写入者约束；内容 fsync 与目录 fsync 均成功后才记为已保存并发送 COMPLETE。失败清理也核对本任务 inode，不删除外来文件。诊断仅记录固定的存储阶段/系统调用名称与 errno 数字，不记录异常中的本地路径。

## 7. 测试向量与验收边界

- [fixture.json](examples/fixture.json)：生成规则、长度、哈希和推荐分帧；不储存 1 MiB 数据副本。
- [happy-session.json](examples/happy-session.json)：控制帧的精确 UTF-8 字符串、头部十六进制与顺序。假指纹仅用于解析测试，不得作为运行期信任凭据；元数据不属于网络消息。
- [terminal-messages.json](examples/terminal-messages.json)：REJECT、任务开始前 ERROR、任务中 ERROR 的独立合法终止消息向量。
- [negative-vectors.json](examples/negative-vectors.json)：严格数字、长度、身份、顺序、远程路径与服务边界的预期拒绝例。`input`、`expected` 等外层字段不是协议字段。

解析、哈希或内存回环测试通过只表示这些局部检查通过。P0 真机验收还需要双方日志关联：原生 P2P 会话、实际 socket 本地/远端地址与端口、接口、TLS 对端身份、文件哈希及保存结果；保网测试要比较双方传输前/中/后的原 AP 和上网连接。分别执行“无共同 AP”和“双方原 Wi-Fi 均保留”两类测试。双方报告保网未经独立观测不能作为结论；本协议不接受对端 JSON 自报 `direct=true` 作为证明。

传输速度结果必须计入真实保存，首轮 1 MiB 仅用于链路正确性，不可用于宣传峰值速度。真实端点不足、未认证或未真机运行时标记 **未验证**，不能标记通过。

## 8. USB 辅助固定数据调试

0.3.0 增加开发用辅助入口，以避免远程 UI 工具的往返延迟耗尽系统配对窗口。它需要设备持有人已授权的 USB 调试渠道；USB 仅交换公钥、nonce、端口和限定实验动作，1 MiB 文件字节仍使用本契约的 TLS 1.3 与原生 P2P 路径。普通应用流程保持逐次系统确认、公钥确认及接收确认。

Android 入口只在 `FLAG_DEBUGGABLE`、显式启动 nonce 与应用私有 bootstrap 文件匹配、bootstrap 对端指纹等于已在 UI 核对的公钥、固定 fixture 预授权为真时启用。不新增导出的控制接收器。私有命令文件最多 16 KiB，严格字段与动作白名单，仅允许 `receive`、`send`、`acceptfixedfixture`、`cancel`；动作绑定活动 nonce 与一次性 commandId，不提供任意路径、文件、设置或无线操作。只有当前已验证的原生 Direct 路径才能收发。普通启动不读取命令，也不自动接受文件。

辅助实验的原生连接窗口最多 600 秒且不滚动延长；每个 TLS 文件会话仍使用原来的 180 秒绝对上限、新平台 TLS 会话、新任务 ID 和禁恢复策略。Android 离开前台或关闭页面后停止辅助命令和文件任务；普通模式的 20 秒建链观察、勾选后的 180 秒文件窗口不变。

预授权只适用于已认证的指定公钥、合法 `OFFER` 中固定 fixture、长度与哈希。报告用 `operatorFixturePreauthorized` / `OperatorFixturePreauthorized` 记录操作者实验预授权；`userAcceptedOffer` / `ReceiverUserAccepted` 不得因此伪报为人工点击。双方真实端点、TLS 身份、字节数、哈希、保存和关闭结果仍是验收所需证据。原始 nonce、私钥、设备报告与个人媒体不公开。具体操作见 [文件实验说明](../docs/p0-file-transfer.md)。
